# Cardly product growth roadmap

## 1. Назначение документа

Этот roadmap описывает следующий этап развития Cardly после стабилизации основного продукта. Он не заменяет текущие документы по архитектуре, дизайну и развёртыванию, а дополняет их продуктовыми milestones.

В roadmap намеренно не включено подключение нового домена. Это отдельная операционная задача, не зависящая от продуктовых milestones ниже.

Текущая основа, на которую опирается план:

- React 19 + TypeScript + Vite на клиенте;
- Express API в Vercel Functions;
- Neon Postgres для карточек, заявок и статистики;
- Vercel Blob для обложек проектов;
- Telegram Mini App для авторизации и нативных действий;
- одна карточка на одного Telegram-пользователя;
- три публичные темы: Clean, Dark и Editorial;
- автосохранение черновика, публикация с публичным snapshot и синхронизация опубликованных изменений;
- события `card_view`, `primary_cta_click`, `link_click`, `project_open`, `share` и `lead_submit`;
- заявки со статусами и Telegram-уведомлениями;
- RU/EN-интерфейс.

## 2. Продуктовое направление

### Пользователь

Основной пользователь Cardly — специалист, фрилансер, консультант или владелец небольшого бизнеса. Он открывает Mini App перед знакомством, встречей, перепиской или публикацией ссылки и хочет быстро представить себя профессионально, передать контакты и понять, заинтересовала ли визитка получателя.

### Основная задача

Cardly должен помогать пройти путь:

> Просмотр → интерес → контакт → заявка → продолжение общения

Каждый milestone должен улучшать один из переходов этого пути, а не просто добавлять новый экран.

### Домен продукта

- первое впечатление;
- профессиональное представление;
- обмен контактами;
- доказательства опыта;
- источник знакомства;
- намерение связаться;
- продолжение разговора;
- измеримый результат визитки.

### Цветовой мир

Новые интерфейсы продолжают существующую систему Cardly:

- тёплый бумажный белый — личное представление и спокойный фон;
- графитовый — профессиональная типографика;
- зелёный и приглушённая мята — готовность, успешная публикация и полезное действие;
- тёплый бежевый — Editorial-подача и портфолио;
- янтарный — незавершённость и требующее внимания состояние;
- приглушённый красный — ошибка или необратимое действие;
- Telegram blue используется только там, где действие действительно принадлежит Telegram.

### Подпись продукта

Узнаваемым элементом Cardly становится **«маршрут визитки»**: владелец видит, как человек нашёл карточку, что посмотрел и совершил ли целевое действие. Эта логика должна проявляться в share-превью, источниках переходов, статистике, готовности карточки и заявках.

### От каких типовых решений отказываемся

- Абстрактные метрики без следующего действия заменяются понятной воронкой визитки.
- Универсальный «процент заполнения профиля» заменяется конкретными советами, влияющими на контакт.
- Тяжёлая CRM с таблицами и множеством полей заменяется компактным inbox заявок внутри Mini App.
- Бесконечная галерея шаблонов заменяется управлением содержанием и порядком разделов в трёх качественных темах.

## 3. Общие правила реализации

Эти требования действуют для всех milestones.

### UX и дизайн

- `App-design.pen` остаётся визуальным источником истины для существующих экранов.
- Новые состояния проектируются в той же системе: Geist/Inter, существующие spacing/radius/icon scales, 44 px touch targets и border-led elevation.
- Mobile-first ширины: 320, 390 и 420 px; дополнительно проверяются 768 и 1440 px.
- Все новые действия имеют loading, success, empty, error и retry состояния.
- Все новые тексты добавляются сразу на RU и EN.
- Новые функции не должны перекрывать Telegram safe areas или нижнюю навигацию.
- Любая анимация поддерживает `prefers-reduced-motion`.

### Архитектура и данные

- Входные данные валидируются Zod-схемами в `shared/` и повторно проверяются сервером.
- Владелец работает только через owner API с Telegram session; публичные endpoints не раскрывают `ownerUid`, Telegram ID и внутренние заметки.
- Миграции выполняются идемпотентно через `ADD COLUMN/TABLE IF NOT EXISTS` либо отдельный безопасный migration script.
- Новые агрегаты не должны смешиваться с demo fixtures в production.
- Сетевые ошибки возвращают контролируемый code и `requestId`.
- События аналитики не блокируют пользовательское действие.
- Не хранить IP, User-Agent, Telegram initData, содержимое заявки или другие персональные данные в продуктовой аналитике.

### Выпуск

- Каждый milestone реализуется в отдельной ветке `codex/<milestone-name>`.
- До реализации добавляются тесты на подтверждённый production-сценарий.
- Обязательны `npm run check` и production-like Playwright для изменённых потоков.
- Сначала Vercel Preview и ручной smoke test, затем merge в `main`.
- Изменения данных выпускаются в backward-compatible порядке: схема → сервер → клиент → cleanup старой совместимости.
- Для рискованных функций предусматривается feature flag или поэтапное включение.

## Milestone 1. Персональное превью ссылки

**Статус:** implemented, Preview verified

**Приоритет:** P0

**Размер:** M
**Зависимости:** нет

### Цель

При отправке публичной визитки Telegram, WhatsApp, VK, iMessage и другие клиенты должны показывать персональное превью конкретной карточки, а не общий заголовок Cardly или пустую ссылку.

### Пользовательский результат

- Получатель ещё до открытия понимает, чья это визитка и чем занимается человек.
- Владелец видит preview перед отправкой и уверен, что ссылка выглядит профессионально.
- Тема и accentPreset узнаваемо отражаются в изображении, но текст остаётся контрастным.

### UX

Превью 1200×630 содержит:

- безопасную Telegram-аватарку или инициалы;
- имя;
- профессию;
- короткий фрагмент bio с ограничением длины;
- подпись Cardly;
- визуальный характер выбранной темы и accentPreset.

На экране публикации появляется компактный блок «Превью при отправке» с:

- актуальным изображением;
- состояниями «Готовим», «Готово», «Не удалось обновить»;
- повторной генерацией только при ошибке;
- пояснением, что внешние приложения могут временно кэшировать старое превью.

### Техническое решение

1. Добавить публичный endpoint генерации OG-изображения, например `GET /api/public/cards/:slug/og.png`.
2. Генерировать изображение сервером через `@vercel/og` или совместимый Vercel runtime.
3. Данные брать исключительно из очищенного `public_data`, чтобы черновик и приватные поля не попадали в превью.
4. Для `/c/:slug` отдавать HTML с динамическими `title`, `description`, `og:*` и `twitter:*` тегами до загрузки SPA.
5. Сохранить прямую работу React Router после загрузки страницы. Предпочтительный вариант — Vercel rewrite на server-rendered HTML shell с подключением Vite assets; перед реализацией требуется небольшой deployment spike на Preview.
6. Добавить cache headers и версию превью, связанную с `lastPublishedAt`, чтобы валидные изменения обновляли cache key.
7. При `pending_validation` продолжать показывать последнюю корректную публичную версию и её превью.
8. Аватар загружать с timeout; при недоступности использовать инициалы, не завершать генерацию ошибкой.

### Изменения контрактов

Можно обойтись без изменения основной схемы БД. В owner publication response добавить вычисляемые поля:

```ts
interface SharePreview {
  imageUrl: string | null
  version: string | null
  status: 'not_published' | 'ready' | 'error'
}
```

### Затрагиваемые зоны

- `server/app/routes.ts` и отдельный модуль OG rendering;
- Vercel rewrites/Function entry;
- `src/pages/publication-page.tsx`;
- `src/features/public-card/*` для общих presentation helpers;
- CSP `img-src` и cache policy;
- документация deployment.

### Тесты

- OG endpoint возвращает `image/png` размером 1200×630.
- Изображение строится только из опубликованного snapshot.
- Непубликованный slug возвращает 404 без утечки данных.
- Отсутствующий/закрытый avatar даёт корректный fallback.
- HTML `/c/:slug` содержит персональные meta tags и продолжает запускать SPA.
- RU/EN и длинные имя/профессия не переполняют изображение.
- После синхронизации опубликованных изменений меняется preview version.

### Критерии готовности

- Telegram показывает имя, профессию и персональное изображение для новой ссылки.
- Lighthouse/crawler получает метаданные без выполнения JavaScript.
- Публичная карточка открывается как раньше на мобильном и desktop.
- Приватные поля отсутствуют в HTML и OG-изображении.

### Риски и защита

- **Кэш Telegram.** Версионировать image URL; показать владельцу понятное пояснение.
- **Холодный старт генерации.** Кэшировать готовый результат и держать шаблон лёгким.
- **Недоступная аватарка.** Всегда иметь deterministic initials fallback.

### Результат реализации

- `/c/:slug` отдаёт crawler-ready HTML с динамическими Open Graph, Twitter Card и canonical metadata до запуска SPA.
- `/api/public/cards/:slug/og.png` генерирует версионированное изображение 1200×630 из последнего опубликованного snapshot.
- Реализованы варианты Clean, Dark и Editorial, все пять accent presets, защищённая загрузка Telegram-аватара и fallback на инициалы.
- На экране публикации отображаются живое preview, состояния синхронизации, ошибка с повтором и пояснение о внешнем кэше.
- Unit, API и UI-тесты, production build и реальный Vercel Preview smoke test пройдены.

## Milestone 2. Источники переходов и воронка визитки

**Статус:** in progress — core implementation and local QA complete

Реализовано в `codex/milestone-2-funnel`: owner CRUD источников, устойчивые ref-токены,
QR/download/share, анонимные идемпотентные события, 90-дневное raw-хранение, связная воронка,
рейтинг источников, small-sample состояния и RU/EN интерфейс. До статуса `implemented` остаются
Vercel Preview smoke test и проверка реального Telegram WebView на production-like API.

**Приоритет:** P0

**Размер:** L
**Зависимости:** Milestone 1 желателен, но не обязателен

### Цель

Показать владельцу, откуда приходят посетители и на каком этапе они перестают взаимодействовать с визиткой.

### Пользовательский результат

Владелец может создать отдельные ссылки или QR-коды для конференции, Telegram-канала, резюме или соцсети и затем увидеть:

- сколько людей открыли каждый источник;
- сколько нажали основной CTA;
- сколько открыли контакт, проект или услугу;
- сколько отправили заявку;
- конверсию между этапами.

### UX создания источника

На экране публикации появляется секция «Ссылки для распространения»:

- список источников с названием, короткой ссылкой и количеством просмотров;
- кнопка «Создать ссылку»;
- предустановки «Мероприятие», «Соцсеть», «Резюме», «Печатный QR» и свободное название;
- действия: поделиться, скопировать, показать/скачать QR, переименовать, архивировать;
- базовая ссылка карточки считается источником «Прямая» и не удаляется.

Нельзя позволять пользователю вручную задавать token. Сервер создаёт случайный непрогнозируемый идентификатор. Архивация прекращает отображение источника в быстрых действиях, но не ломает уже распечатанный QR.

### UX статистики

Вкладка «Статистика» получает:

1. **Маршрут визитки** — последовательность `Просмотры → Интерес → Контакты → Заявки`.
2. **Источники** — ранжированный список с просмотрами и конверсией.
3. **Интерес** — существующие CTA/link/project события, но сгруппированные понятным языком.
4. Переключатели 7/30/всё время продолжают работать для всех новых блоков.

При малом объёме данных не показывать вводящие в заблуждение проценты. До достижения минимальной выборки выводить абсолютные значения и текст «Недостаточно данных для устойчивого вывода».

### Модель данных

Добавить таблицу кампаний:

```sql
cardly_share_sources (
  id uuid primary key,
  owner_uid text not null,
  card_slug text not null,
  name text not null,
  token text not null unique,
  archived boolean not null default false,
  created_at timestamptz not null,
  updated_at timestamptz not null
)
```

Для корректной воронки агрегированных счётчиков недостаточно. Добавить privacy-safe журнал событий с ограниченным сроком хранения:

```sql
cardly_analytics_events (
  event_id uuid primary key,
  owner_uid text not null,
  card_slug text not null,
  event_type text not null,
  source_id uuid null,
  visit_id_hash text not null,
  occurred_at timestamptz not null
)
```

Правила:

- `visitId` генерируется клиентом для сессии публичной карточки;
- сервер хранит только HMAC/hash с server secret;
- не сохраняются IP, User-Agent или Telegram ID посетителя;
- `eventId` обеспечивает идемпотентность повторной отправки;
- raw events хранятся ограниченный период, например 90 дней;
- текущие daily/all-time агрегаты продолжают обновляться для быстрых totals.

### API

- `GET /api/owner/share-sources`
- `POST /api/owner/share-sources`
- `PATCH /api/owner/share-sources/:id`
- `GET /api/owner/stats?period=7|30|all` расширяется `funnel` и `sources`
- `POST /api/public/cards/:slug/events` принимает optional `sourceToken`, `visitId`, `eventId`

Публичный URL имеет вид `/c/:slug?ref=<token>`. Неизвестный или архивированный token не блокирует открытие карточки и учитывается как direct/unknown по выбранной серверной политике.

### Семантика воронки

- **Просмотр:** уникальный `visit_id_hash` с `card_view`.
- **Интерес:** уникальный визит с `project_open`, `service_open` или другим содержательным действием. Если `service_open` добавляется впервые, событие должно иметь реальное действие в UI, а не срабатывать от прокрутки.
- **Контакт:** `primary_cta_click` либо `link_click` для контактной ссылки.
- **Заявка:** `lead_submit` после успешного ответа API.

Один визит учитывается максимум один раз на каждом уровне, но все raw actions остаются доступны для breakdown.

### Тесты

- CRUD источников доступен только владельцу.
- Token непредсказуем, уникален и не раскрывает uid/slug.
- `ref` проходит строгую валидацию и не попадает в HTML без escaping.
- Повторный `eventId` не удваивает статистику.
- Один visit с несколькими clicks считается один раз на соответствующем уровне funnel.
- 7/30/all корректно фильтруют funnel и sources.
- Старые события без source продолжают учитываться как direct.
- Lead связывается с source без раскрытия посетительских данных владельцу.

### Критерии готовности

- Владелец создаёт ссылку и QR за один поток без ухода с публикации.
- Переход по source URL открывает ту же публичную карточку.
- В статистике источник появляется после реального просмотра.
- Воронка математически согласована: следующий этап не превышает предыдущий в рамках уникальных визитов.
- На нулевых данных показывается понятное empty state.

### Риски и защита

- **Рост таблицы событий.** Индексы по owner/time/source, retention cleanup и агрегирование старых данных.
- **Ad blockers/закрытие страницы.** Использовать `sendBeacon`/`keepalive` с безопасным fallback.
- **Ложная точность.** Показывать абсолютные числа и nullable conversion при малой выборке.

## Milestone 3. Индикатор готовности визитки

**Статус:** planned

**Приоритет:** P1

**Размер:** M
**Зависимости:** нет

### Цель

Помогать владельцу улучшить карточку конкретными советами, не превращая заполнение в бессмысленную игру с процентами.

### Пользовательский результат

Владелец сразу понимает:

- можно ли уже отправлять карточку;
- чего не хватает для контакта;
- какое одно улучшение даст наибольшую пользу;
- какие замечания блокируют публикацию, а какие являются рекомендациями.

### Модель оценки

Создать чистую функцию `evaluateCardReadiness(card)` в `shared/`. Она возвращает не только score, но и объяснимые правила:

```ts
interface CardReadiness {
  level: 'incomplete' | 'ready' | 'strong'
  score: number
  blocking: ReadinessIssue[]
  recommendations: ReadinessIssue[]
  strengths: ReadinessStrength[]
  nextBestAction: ReadinessIssue | null
}
```

Категории правил:

- **Представление:** имя, профессия, содержательное bio.
- **Контакт:** рабочий primary CTA и хотя бы один валидный способ связи.
- **Доверие:** навыки, услуга или проект с достаточным содержанием.
- **Конверсия:** понятный CTA и включённая форма заявки либо альтернативный контакт.
- **Публикация:** свободный slug, валидный snapshot, synced state.

Score используется для сортировки советов и аналитики интерфейса, но пользователю в первую очередь показываются уровень и действия. Нельзя штрафовать пользователя за сознательно отключённые необязательные разделы.

### UX

- На вкладке «Визитка» — компактный статус под публикацией: «Можно отправлять» или «Нужно исправить 2 пункта».
- В редакторе — блок «Следующее улучшение» со ссылкой сразу на нужное поле/раздел.
- На публикации — blocking issues отделены от non-blocking recommendations.
- После выполнения рекомендации состояние обновляется локально без ожидания нового bootstrap.
- В onboarding правила используются только для подсказок и финальной проверки, не добавляя лишних шагов.

### Правила текста

Плохой текст: «Профиль заполнен на 67%».

Хороший текст: «Добавьте способ связи — сейчас посетитель не сможет написать вам».

Каждая рекомендация содержит:

- причину;
- ожидаемый результат;
- одну кнопку перехода;
- RU/EN формулировки.

### Данные и API

На первом этапе отдельные колонки БД не требуются. Readiness вычисляется на клиенте из draft и на сервере при публикации из той же shared-функции/правил. Сервер остаётся авторитетным для blocking validation.

Опционально после Milestone 8 можно отправлять обезличенные события `readiness_recommendation_opened/completed`, но не содержимое полей.

### Тесты

- Чистый initial draft имеет ожидаемые blocking issues.
- Валидная минимальная карточка получает `ready`.
- Проект без изображения не блокирует публикацию, если изображение необязательно.
- Отключённый раздел не создаёт ложную рекомендацию заполнить его.
- Invalid URL становится blocking только когда соответствующий публичный элемент включён.
- `nextBestAction` детерминирован и ведёт на существующий owner route.
- RU/EN покрывают все rule IDs.

### Критерии готовности

- На каждом состоянии карточки показывается максимум одно главное следующее действие.
- Индикатор не противоречит серверной publish validation.
- Выполнение совета обновляет состояние до следующего автосохранения.
- Интерфейс не блокирует публикацию из-за необязательных рекомендаций.

### Риски и защита

- **Манипулятивная геймификация.** Не использовать streaks, конфетти и искусственные штрафы.
- **Расхождение с Zod.** Blocking rules строить поверх publishable schema и общих rule IDs.
- **Перегрузка советами.** Один next best action плюс сворачиваемый полный список.

## Milestone 4. Компактный inbox заявок

**Статус:** planned

**Приоритет:** P1

**Размер:** L
**Зависимости:** Milestone 2 для отображения источника заявки

### Цель

Позволить владельцу не только увидеть заявку, но и довести её до следующего контакта внутри лёгкого mobile-first workflow.

### Продуктовая граница

Cardly не становится полноценной CRM. Не добавляются компании, сделки, pipelines, роли, команды и произвольные custom fields. Inbox решает четыре задачи:

1. понять, кто написал;
2. быстро связаться;
3. сохранить короткий контекст;
4. не забыть продолжить разговор.

### UX

Вкладка «Заявки» получает:

- badge непросмотренных в переключателе Статистика/Заявки и, при необходимости, в нижней навигации;
- фильтры «Новые», «В работе», «Завершённые», «Архив»;
- поиск по имени и контакту;
- карточку с именем, датой, источником, фрагментом сообщения и следующим действием;
- detail bottom sheet на mobile и side panel на desktop;
- действия «Написать», «Позвонить/открыть контакт», «Скопировать», «Завершить»;
- заметку владельца до разумного лимита, например 1000 символов;
- необязательную дату «Напомнить»;
- экспорт текущего отфильтрованного списка в CSV.

Quick action определяется безопасно:

- `@username` и `https://t.me/...` открываются через `openTelegramLink`;
- `mailto:`/email и `tel:` используются только после строгой нормализации;
- неизвестный формат только копируется и никогда не вставляется напрямую в URL.

### Модель данных

Расширить `cardly_leads`:

```sql
ALTER TABLE cardly_leads
  ADD COLUMN IF NOT EXISTS owner_note text NOT NULL DEFAULT '',
  ADD COLUMN IF NOT EXISTS follow_up_at timestamptz NULL,
  ADD COLUMN IF NOT EXISTS updated_at timestamptz NOT NULL DEFAULT NOW();
```

Статусы привести к продуктовым:

```ts
type LeadStatus = 'new' | 'in_progress' | 'completed' | 'archived'
```

Backward-compatible rollout:

1. Сервер временно читает старый `read` как `in_progress`.
2. Миграция обновляет существующие строки `read → in_progress`.
3. Клиент выпускается с новым enum.
4. Совместимость удаляется после production verification.

Заметка и reminder являются owner-only и никогда не включаются в публичные ответы или уведомления посетителю.

### API

- `GET /api/owner/leads?status=&query=&cursor=&limit=` с cursor pagination.
- `GET /api/owner/leads/:id`.
- `PATCH /api/owner/leads/:id` для status, note и follow-up.
- `GET /api/owner/leads/export.csv?...` с UTF-8 BOM, локализованными заголовками и защитой от CSV formula injection.
- Bootstrap возвращает только summary: recent leads и counts. Полный список грузится при открытии вкладки.

### Напоминания

В первой версии reminder отображается внутри приложения и в счётчике просроченных. Отправка scheduled Telegram notification требует отдельной фоновой инфраструктуры и не входит в milestone, пока не будет выбран безопасный scheduler.

### Тесты

- Владелец не может читать/менять чужую заявку.
- Pagination стабильна при новых входящих заявках.
- Поиск и фильтры работают с RU/EN текстом.
- Owner note не появляется в dashboard analytics/public API/logs.
- CSV экранирует формулы, кавычки, переносы строк и корректно открывается с кириллицей.
- Quick actions не создают `javascript:`/произвольные URL.
- Новый lead увеличивает badge без полного перезапуска.
- Старый `read` корректно мигрирует в `in_progress`.

### Критерии готовности

- Новая заявка видна без перезапуска Mini App.
- Владелец может за два действия перейти к контакту.
- Заметка и статус сохраняются с retry/error feedback.
- Экспорт отражает выбранный фильтр и не содержит внутренних идентификаторов.

### Риски и защита

- **Утечка заметок.** Отдельные owner DTO и explicit column selection.
- **Большой bootstrap.** Cursor pagination и только recent summary при auth.
- **Опасный CSV.** Prefix для значений, начинающихся с `=`, `+`, `-`, `@`.

## Milestone 5. Оптимизация и кадрирование изображений проектов

**Статус:** planned

**Приоритет:** P1

**Размер:** M
**Зависимости:** нет

### Цель

Сделать загрузку обложки предсказуемой на мобильном устройстве, ускорить публичные карточки и уменьшить расход Blob-хранилища и трафика.

### UX

Поток загрузки:

1. Пользователь выбирает JPG, PNG или WebP до текущего входного лимита.
2. Приложение показывает локальное превью сразу, до сети.
3. Открывается простой crop editor с рамкой 16:10, zoom и перемещением.
4. После подтверждения интерфейс показывает отдельные этапы «Обрабатываем» и «Загружаем».
5. В случае ошибки выбранное изображение и crop сохраняются для повторной попытки.
6. После успеха обновляются preview проекта, draft и публичный snapshot опубликованной карточки.

Кнопка закрытия во время обработки предлагает отменить операцию; `AbortController` прекращает upload, если это поддерживается клиентом Blob.

### Обработка

- учитывать EXIF orientation через browser decode/createImageBitmap;
- output ratio 16:10;
- максимальный output примерно 1600×1000;
- WebP quality около 0.82 с возможностью адаптивного понижения до целевого размера;
- целевой размер 300–800 КБ, жёсткий предел после обработки 1.5 МБ;
- не увеличивать маленькие изображения;
- освобождать object URLs и canvas buffers после завершения;
- при нехватке памяти показать контролируемую ошибку и предложить выбрать файл меньшего размера.

Параметры должны быть вынесены в тестируемый config, а не разбросаны magic numbers по компонентам.

### Хранение и lifecycle

- Новый blob загружается в `users/<uid>/project/` как сейчас.
- Старый blob удаляется только после успешной загрузки нового и принятия нового URL в draft.
- Если autosave нового URL не удался, старое изображение не удаляется.
- Для orphan uploads добавить dry-run cleanup script по возрасту; автоматическое удаление включать только после проверки отчёта.
- `coverUrl` по-прежнему проходит публичную очистку и domain validation.

### Архитектура клиента

Выделить:

- `image-processing-service.ts` — decode/crop/resize/encode;
- `project-cover-crop-dialog.tsx` — доступный crop UI;
- существующий `image-upload-service.ts` — только transport/auth/progress;
- reducer/state machine со стадиями `idle → preparing → cropping → processing → uploading → saving → success/error`.

Это устранит неопределённое состояние «0%», когда обработка или token generation ещё не начались.

### Сервер

- Сохранить server-side MIME/size/path validation.
- Не доверять расширению файла.
- Добавить `image/jpeg`, `image/png`, `image/webp`; AVIF включать только после проверки decode на целевых Telegram WebView.
- Логировать stage и requestId без имени исходного файла.

### Тесты

- Large JPEG преобразуется в WebP нужного ratio и предела.
- Portrait/rotated image получает правильную ориентацию.
- Small image не увеличивается.
- Cancel освобождает ресурсы и не изменяет draft.
- Ошибка обработки не начинает upload.
- Ошибка upload сохраняет возможность retry.
- Старый blob удаляется только после успешной замены.
- Public Clean/Dark/Editorial показывают одинаково стабильный crop.
- Android-like E2E не остаётся бесконечно на 0%.

### Критерии готовности

- На нормальном мобильном соединении UI меняет состояние не позднее 100 мс после выбора файла.
- Пользователь всегда понимает, идёт обработка или сеть.
- Публичная обложка не прыгает по высоте и совпадает с выбранным crop.
- Повторная загрузка не оставляет прежнюю обложку после успешного save/sync.

### Риски и защита

- **Память слабых Android устройств.** Ограничить decode size и обрабатывать последовательно.
- **Разница WebView codecs.** Feature detection и WebP fallback policy.
- **Orphan blobs.** Отчётный cleanup с dry-run и `--confirm`.

## Milestone 6. Управление порядком разделов

**Статус:** planned

**Приоритет:** P2

**Размер:** L
**Зависимости:** Milestone 3 желателен для подсказок о структуре

### Цель

Позволить владельцу адаптировать историю визитки под профессию, сохранив качество трёх разработанных тем.

### Продуктовые правила

- Profile/hero и основной CTA всегда остаются в верхней части карточки.
- Footer и системные действия остаются внизу.
- Пользователь меняет порядок содержательных разделов: навыки, услуги, проекты, контакты и форма заявки.
- Скрытый раздел сохраняет позицию и возвращается туда же после включения.
- Пустой или невалидный раздел не попадает в public snapshot независимо от позиции.

### Использование текущей модели

`appearance.visibleSections` уже является массивом section IDs. Его нужно сделать единственным авторитетным источником порядка и видимости вместо добавления второго поля `sectionOrder`.

Перед выпуском:

- усилить Zod validation: уникальные section IDs без дублей;
- миграционно дополнять отсутствующие IDs дефолтным порядком;
- сохранить временную совместимость с `showSkills/showServices/showProjects/showContactForm`;
- после обновления всех клиентов решить отдельной миграцией, нужны ли legacy booleans.

### UX редактора

В «Оформлении» секция «Порядок и видимость» заменяет простой список toggle:

- drag handle для touch/mouse;
- явные кнопки «Выше» и «Ниже» как доступный fallback;
- toggle видимости;
- короткий content summary, например «3 проекта»;
- live preview прокручивается/подсвечивает перемещённый раздел;
- сохранение использует существующую autosave queue.

На 320 px строка должна сохранять 44 px targets и не иметь горизонтального overflow. Drag не должен перехватывать обычный вертикальный scroll, пока пользователь не начал движение за handle.

### Рендеринг публичной карточки

Каждая тема получает собственный registry section renderers и композиционные ограничения, но читает общий order:

- Clean сохраняет спокойные белые секции;
- Dark сохраняет техническую сетку и моноширинные маркеры;
- Editorial сохраняет нумерацию, автоматически пересчитывая номера по фактическому порядку.

Нельзя собирать все темы из одного универсального card component: порядок общий, художественная композиция остаётся отдельной для каждой темы.

### Изменения public snapshot

Sanitizer должен:

- сохранять валидный уникальный порядок;
- удалять отключённые/невалидные элементы;
- не оставлять пустые секции и лишние разделители;
- корректно обрабатывать старые snapshots без полного массива IDs.

### Тесты

- Порядок сохраняется после перезапуска и публикации.
- Скрытый раздел возвращается в прежнюю позицию.
- Duplicate/unknown IDs отклоняются или нормализуются сервером.
- Все три темы следуют одному order без потери собственной композиции.
- Editorial numbering пересчитывается.
- Keyboard buttons и pointer drag дают одинаковый результат.
- Автосохранение во время быстрой перестановки не откатывает новый order.
- Нет overflow на 320/390/420 и layout shift при пустом разделе.

### Критерии готовности

- Порядок в preview полностью совпадает с `/c/:slug` после sync.
- Любой раздел можно переместить без случайного скролла страницы.
- Публичная карточка остаётся визуально цельной во всех допустимых порядках.
- Старые опубликованные карточки продолжают отображаться без ручного редактирования.

### Риски и защита

- **Разрушение художественной композиции.** Ограничить reorder только содержательными секциями и отдельно QA каждого theme/order class.
- **Touch-конфликт.** Handle-only drag и кнопки fallback.
- **Legacy booleans.** Двухэтапная миграция без немедленного удаления полей.

## Milestone 7. Нативные возможности Telegram

**Статус:** planned

**Приоритет:** P2

**Размер:** M
**Зависимости:** Milestone 1 для Story/share media; стабильная production telemetry желательна

### Цель

Сделать Cardly естественной частью Telegram, не показывая неподдерживаемые кнопки и не заставляя пользователя соглашаться на навязчивые prompts.

### Возможности milestone

#### 7.1. Добавление на домашний экран

- Расширить typed Telegram adapter методами `checkHomeScreenStatus`, `addToHomeScreen` и событиями результата.
- Показывать предложение только если API поддерживается и status равен `missed`/`unknown`.
- Не показывать prompt в onboarding, при ошибке, до первой публикации или при первом запуске.
- Рекомендуемый trigger: после второй успешной сессии либо после первой успешной публикации/отправки.
- После отказа поставить cooldown, например 30 дней, в local/device storage.
- В профиле оставить ручное действие «Добавить на главный экран», если поддерживается.

#### 7.2. Отправка карточки в Telegram Story

- Если `shareToStory` поддерживается, показывать отдельное действие «В историю» рядом с обычным share.
- Использовать публичное вертикальное изображение, созданное на основе Milestone 1, а не screenshot DOM.
- Добавлять link widget на публичную карточку только в рамках разрешённых Telegram параметров.
- Если API недоступно, кнопку полностью скрывать, а не показывать ошибку.

#### 7.3. Аудит нативных действий

- BackButton остаётся авторитетным для возврата из owner preview/editor depth.
- Haptic feedback используется только на успех, предупреждение и значимое переключение, без вибрации на каждый tap.
- Telegram link открывается через `openTelegramLink`, внешняя HTTPS-ссылка — через `openLink` с browser fallback.
- Цвет header/background синхронизируется с активной owner theme и safe-area поведением.
- Проверить поддержку новых методов по Telegram version/capability, а не только по наличию глобального объекта.

#### 7.4. Настройка профиля Main Mini App

Операционный checklist в `docs/telegram-setup.md`:

- включить Main Mini App;
- загрузить RU/EN screenshots и короткое demo video;
- проверить launch button и menu button;
- проверить loading-screen icon/colors;
- убедиться, что startapp slug продолжает открывать чужую карточку без owner controls.

### Данные

Серверная схема не требуется. Локально хранить только:

- количество успешных запусков;
- дату последнего home-screen prompt;
- факт подтверждённого добавления, если Telegram его сообщает.

Эти данные не являются критичными и не синхронизируются между устройствами.

### Тесты

- Unsupported API не создаёт кнопки/ошибки.
- Prompt не появляется в onboarding и до публикации.
- Cooldown соблюдается после отказа.
- `added` больше не предлагает действие.
- Story action использует публичный media URL и link widget.
- Чужая карточка не получает owner navigation.
- BackButton и browser history не создают двойной переход.
- Safe area проверена на Android/iOS/desktop mocks.

### Критерии готовности

- Все native actions появляются только на поддерживаемых клиентах.
- Ни один системный prompt не показывается без контекста и явного действия пользователя.
- Публичная карточка корректно открывается из Story/startapp ссылки.
- RU/EN media preview и профиль бота проверены вручную.

### Риски и защита

- **Разный уровень поддержки Telegram клиентов.** Capability detection и полный web fallback.
- **Навязчивый prompt.** Контекстный trigger, cooldown и ручная настройка.
- **Owner control на чужой карточке.** Сохранять текущую проверку owner preview intent/session, не выводить управление только по slug.

## Milestone 8. Наблюдаемость и контроль качества production

**Статус:** planned

**Приоритет:** P0 для инфраструктуры, выпускать поэтапно

**Размер:** M
**Зависимости:** нет; желательно начать baseline до Milestone 2

### Цель

Находить ошибки, зависания и деградацию скорости до того, как пользователь пришлёт скриншот, сохраняя приватность владельцев и посетителей.

### Что измеряем

#### Надёжность

- ошибки auth/bootstrap;
- неуспешный autosave и размер очереди;
- publish/unpublish timeout/error;
- upload stage, timeout и failure;
- public card 404/5xx;
- lead submit и Telegram notification failure;
- analytics ingestion failure;
- ErrorBoundary с route и release version.

#### Производительность

- auth/bootstrap duration;
- first contentful owner state;
- переходы между owner routes;
- INP/LCP/CLS публичных карточек;
- decode/process/upload duration изображения;
- OG generation latency;
- API p50/p75/p95 по безопасному route template.

#### Продуктовое здоровье

- доля завершённых onboarding;
- доля опубликованных карточек;
- доля publish errors по code;
- доля успешных uploads;
- доля карточек с хотя бы одним реальным просмотром;
- путь `view → contact → lead` после Milestone 2.

### Инструменты

Рекомендуемый минимальный стек:

- Vercel Speed Insights для реальных Web Vitals;
- Vercel logs/observability для Function errors и latency;
- Sentry или эквивалент для client exceptions, releases и source maps;
- существующий structured logger с `requestId` для server correlation.

Подключение внешнего error provider выполняется через adapter, чтобы UI и server не зависели напрямую от SDK. Если Sentry не выбран, интерфейс adapter остаётся и использует безопасный console/Vercel transport.

### Privacy policy telemetry

Разрешённые поля:

- release/commit;
- route template, например `/c/:slug`, но не сам slug;
- Telegram platform/version без user ID;
- stage, duration, error code, requestId;
- connection class при наличии и без fingerprinting.

Запрещённые поля:

- имя, username, Telegram ID;
- initData, session token/cookie;
- slug владельца;
- текст карточки, контакты, заметки и заявки;
- URL query целиком;
- Blob filename пользователя.

Перед отправкой error context должен проходить central sanitizer. Session replay не включать по умолчанию.

### Реализация

1. Добавить `observability` client/server adapters и единый event vocabulary.
2. Прокидывать `x-request-id` в `ApiError` и пользовательский error state.
3. Добавить release identifier из Vercel commit SHA без runtime secret.
4. Инструментировать критические transitions через Performance API.
5. Подключить Web Vitals с sampling, подходящим тарифу.
6. Добавить health smoke после Preview/Production deploy.
7. Описать dashboards, alert thresholds и процедуру triage в `docs/operations.md`.

### SLO и бюджеты

Стартовые целевые значения, которые уточняются после baseline:

- API availability критических owner/public routes ≥ 99.5%;
- owner warm start p75 ≤ 2.5 s;
- переход загруженного owner route p75 ≤ 500 ms;
- INP p75 ≤ 200 ms;
- CLS p75 ≤ 0.1;
- publish/unpublish success ≥ 99%;
- image upload success ≥ 97% для валидных файлов и поддерживаемой сети.

Alert не должен срабатывать по одному пользователю. Использовать окно, минимальный объём событий и сочетание error rate + absolute count.

### UX ошибок

- Пользователь видит локализованную причину и короткий `requestId`.
- Технические stack traces остаются только в telemetry.
- Retry сохраняет введённые данные.
- При массовом сбое owner shell показывает стабильное состояние, а публичная карточка не раскрывает внутреннюю ошибку.

### Тесты

- Sanitizer удаляет PII, tokens, query и slug.
- ApiError сохраняет requestId из response header/body.
- Telemetry transport никогда не блокирует основное действие.
- Offline не создаёт бесконечную очередь событий.
- Sampling детерминирован на сессию и управляется env.
- Source maps не публикуются как открытые assets.
- Performance marks закрываются на success/error/cancel.
- Production-like E2E проверяет, что тестовый failure коррелируется по requestId.

### Критерии готовности

- По production incident можно определить route, release, stage и requestId без доступа к пользовательским данным.
- Есть dashboard минимум для auth, publish, upload, lead submit и public performance.
- Есть документированный alert/triage workflow.
- Телеметрия не ухудшает запуск и не ломает CSP.

### Риски и защита

- **Случайный сбор PII.** Central allowlist sanitizer, тесты и code review checklist.
- **Стоимость.** Sampling, quotas и alerts по использованию.
- **Шум.** Группировка по error code/release/route template и минимальный event volume.

## 4. Рекомендуемая последовательность выпусков

Техническая последовательность отличается от номера продукта только тем, что минимальный observability baseline полезно установить раньше больших изменений.

### Release A — представление и baseline

1. Минимальная часть Milestone 8: requestId correlation, client errors и performance baseline.
2. Milestone 1: персональное share-превью.
3. Milestone 5: обработка изображений.

**Результат:** карточка быстрее загружается, лучше выглядит при отправке, а production-проблемы становятся видимыми.

### Release B — измеримый результат

1. Milestone 2: источники и воронка.
2. Milestone 3: готовность карточки.
3. Расширение Milestone 8 под новые события.

**Результат:** владелец понимает качество карточки и реальный путь посетителей.

### Release C — продолжение общения

1. Milestone 4: компактный inbox заявок.
2. Связь заявки с source из Milestone 2.

**Результат:** Cardly помогает не потерять состоявшийся контакт.

### Release D — персонализация и Telegram growth

1. Milestone 6: порядок разделов.
2. Milestone 7: home-screen и Story actions.

**Результат:** визитка лучше адаптируется под профессию и естественнее распространяется внутри Telegram.

## 5. Глобальная Definition of Done

Milestone считается завершённым только когда:

- пользовательский сценарий работает в реальном Telegram Web/Mobile, а не только в demo mode;
- контракты и миграции backward compatible;
- обновлены RU/EN тексты;
- есть loading, empty, error, retry и unsupported states;
- нет горизонтального overflow на 320/390/420 px;
- изменённые действия доступны с клавиатуры и имеют accessible names;
- unit/component/API тесты покрывают бизнес-правила;
- production-like Playwright покрывает основной happy path и одну критическую ошибку;
- `npm run check` проходит;
- Vercel Preview проверен через `/api/health` и ручной smoke test;
- документация architecture/security/deployment обновлена при необходимости;
- после production deploy проверены telemetry и rollback path.

## 6. Явно не входит в этот roadmap

- подключение или покупка нового домена;
- несколько карточек на одного владельца;
- командные аккаунты и роли;
- полноценная CRM и pipeline продаж;
- платные тарифы, Telegram Stars и подписки;
- публичный каталог визиток;
- AI-генерация текстов без отдельной продуктовой проверки;
- произвольный HTML/CSS редактор тем;
- автоматические Telegram reminders без выбранного scheduler и отдельного consent flow.

Эти направления можно рассматривать после получения реальных данных из Milestones 2 и 8.
